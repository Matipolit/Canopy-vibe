# MCP server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An LLM, through MCP, reads and edits the running canopy's project and measures and
looks at its sound, every edit one undo step, nothing able to crash canopy or touch the audio.

**Architecture:** `crates/mcp` holds the protocol, the tool table and a `Host` trait; the
stdio bridge `canopy-mcp` answers from the table and forwards calls over loopback TCP to the
app, whose `ui/src/mcp/` runs them on the UI thread each frame against the `Session`.
`crates/analysis` measures and draws renders made off the UI thread, with stem capture in
`engine::Bounce`.

**Tech Stack:** Rust 2024; `serde_json` (protocol, hand-written, no async runtime);
`getrandom` 0.3 (token); `realfft`; `tiny-skia`, `png`, `ab_glyph` (images; all already in
`Cargo.lock`); egui_kittest for UI tests.

**Spec:** `docs/superpowers/specs/2026-10-29-mcp-design.md` (read it first; this plan argues
from it). Also read `CLAUDE.md` (architecture rules, conventions, test commands).

## Global Constraints

- Saving, open/new/close/quit, audio settings, plugin editors, MIDI learn, the patcher,
  modulation and deleting files are not reachable from any tool.
- Every project change goes through `Session::edit` (one undo step) with the LLM origin;
  every chain edit ends in `normalize_routing` (the existing edit functions already do).
- Nothing allocates on the audio thread or its workers (stem capture included).
- Time in beats (f64 quarter notes, 960 ticks each), "bar.beat" in reads; MIDI 60 = "C3";
  parameters in descriptor units; choices by label; out of range is an error stating the
  range, never a clamp.
- Limits: 16 MB per message; 10,000 notes per write; 200 operations per batch; 64 tracks per
  arrangement call; notes paged 2000 at a time; renders ≤ 10 min of audio; 2 renders at
  once; render cache 512 MB; images default 1024×512, max 1600×1000; ~4 ms of calls a frame.
- Loopback `127.0.0.1` only; 256-bit token, constant-time compare, 2 s to send it; token file
  `{port, token, pid}` user-only, atomic, removed on quit: `$XDG_CACHE_HOME` or
  `~/.cache/canopy/mcp.json`, `%LOCALAPPDATA%\canopy\mcp.json` on Windows.
- Comments and docs in the codebase's voice (CLAUDE.md "Conventions"); tests named as
  sentences; new UI behaviour gets a `ui_tests` case; sizes from `theme`.
- Use `CARGO_TARGET_DIR=target/mcp` for builds.

## Review Focus

1. A tool call arriving while the user drags a knob: the edit must wait for the gesture to
   end, not join it (test in Task 5).
2. Edits arriving after the user switched "Allow LLM connections" off mid-session, or while
   an export dialog is open: refused or waiting, never applied (Task 5).
3. A batch whose later operation fails after earlier ones created tracks: nothing remains,
   no undo step (Task 6).
4. The project edited (or undone) while a render for `analyze` is running: the result is
   marked stale and not cached (Task 16).
5. The bridge started before canopy, and canopy restarted mid-session: calls fail cleanly
   and then work again without restarting the client (Task 4).

- Produces (`mcp::connection`):

  - `pub fn file_path() -> Option<PathBuf>` (honours `CANOPY_MCP_FILE` for tests, then the

  is retried once on a fresh connection; any other tool gets an error saying it may or may
  not have happened. Replies from the app are copied to stdout as they arrive (progress
  notifications included).
